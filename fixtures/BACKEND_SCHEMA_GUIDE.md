# SkyNet Telemetry Schema Guide (v1.0.0)

This directory contains test JSON fixtures designed for backend engineers implementing ingestion APIs, database models, and SIEM parsers for the SkyNet endpoint security agent.

---

## 1. Fixture Files Overview

| File | Format | Description |
|---|---|---|
| `batch_payload.json` | JSON Object | Full HTTP/REST ingestion payload containing host metadata, a batch of events, and correlated alerts. |
| `events.jsonl` | JSON Lines | Streaming log format emitted by the agent to disk and transport pipelines. |
| `alerts.json` | JSON Array | High-confidence security alerts generated by local multi-event correlation rules. |
| `host.json` | JSON Object | Host identity, kernel, OS, and agent version snapshot. |
| `auth_events.json` | JSON Array | Authentication telemetry (failed/successful logins, sudo, useradd, group change, password change). |
| `process_events.json` | JSON Array | Process execution, process termination, web shells, and temporary folder executions. |
| `network_events.json` | JSON Array | Listening sockets, outbound connections, and ARP changes. |
| `file_and_usb_events.json` | JSON Array | File integrity changes (`/etc/shadow`, `/etc/sudoers`) and USB plug/mount/unplug events. |
| `system_and_app_events.json` | JSON Array | Kernel segfaults, OOM kills, log truncation, SQL injection attempts, crontabs, and webcam/mic access. |

## 2. Top-Level Event Schema

Every telemetry event conforms to this canonical structure:

```typescript
interface Event {
  event_id: string;             // UUIDv4 (unique per event, primary key for deduplication)
  schema_version: string;       // "1.0.0"
  event_type: string;           // Dot-notated event type (e.g. "auth.login_failed")
  category: Category;           // High-level domain
  timestamp: string;            // ISO-8601 UTC timestamp of occurrence ("2026-10-04T12:01:01Z")
  observed_at: string;          // ISO-8601 UTC timestamp when collector observed the event
  host_id: string;              // Persistent machine identifier (from /etc/machine-id)
  hostname: string;             // System hostname
  actor: string;                // Primary entity responsible (username, IP, or PID)
  severity: Severity;           // Severity rating
  source: string;               // Originating file, socket, or subsystem
  collector_status: string;     // "ok", "partial", or "error"
  related_event_ids: string[];  // Array of UUIDs linking prior causal events
  details: Record<string, any>; // Category-specific payload (see section 4)
}
```

---

## 3. Enumerations

### Category
- `auth`: Authentication and user management
- `process`: Process creation, lifecycle, and resource utilization
- `network`: Sockets, ports, outbound connections, and ARP
- `file`: File integrity monitoring and critical path changes
- `usb`: Removable devices and mounts
- `system`: Kernel messages, crashes, and log tampering
- `application`: Web server attacks, database failures, crontabs, extensions, media access
- `agent`: Agent lifecycle (`agent.started`, `agent.stopped`)

### Severity
- `info`: Routine baseline telemetry (successful login, normal process start)
- `low`: Minor anomalies (single failed password)
- `medium`: Notable administrative or operational changes (sudo command, service failure)
- `high`: Suspicious behavior (execution from `/tmp` or USB, privilege group assignment)
- `critical`: Confirmed multi-stage attack or log tampering

## 4. Alert Schema

When the agent's local correlation engine detects a multi-event attack sequence, it emits an `Alert` linking the causal events:

```typescript
interface Alert {
  alert_id: string;             // UUIDv4
  rule_id: string;              // Correlation rule identifier
  severity: Severity;           // Usually "high" or "critical"
  confidence: number;           // Float between 0.0 and 1.0
  explanation: string;          // Human-readable summary of the attack chain
  first_seen: string;           // ISO-8601 UTC timestamp of first event in sequence
  last_seen: string;            // ISO-8601 UTC timestamp of triggering event
  related_event_ids: string[];  // Array of event_id UUIDs that triggered this alert
}
```

### Supported Correlation Rules
1. `brute_force_success`: >= 5 failed logins followed by successful login from same source
2. `account_persistence`: New user creation followed by immediate addition to `sudo`/`admin`
3. `usb_execution`: USB connected -> mounted -> binary executed from mount path
4. `web_to_shell`: Web server (`nginx`, `apache2`) spawns interactive shell (`bash`, `sh`)
5. `download_to_run`: File downloaded into `~/Downloads` followed by execution
6. `log_tampering`: Log truncation/clearing near other high-severity events

---

## 5. Backend Database Recommendations

- **Primary Key**: Use `event_id` (UUID) as the primary key. Ingestion should be idempotent (e.g. `ON CONFLICT (event_id) DO NOTHING`).
- **Composite Index**: `(host_id, timestamp DESC)` for fast time-series filtering per endpoint.
- **Category Index**: `(category, timestamp DESC)` for incident response queries.
- **Details Column**: Store `details` as a `JSONB` column (PostgreSQL) or document field (MongoDB/Elasticsearch) to support flexible querying across different event types.
